# 纸短情长：上线前关键问题整理

## 1. 用户注册与增长

### 1.1 用户需不需要注册？

结论：需要注册，但第一版要尽量轻。

原因：

- 信件需要有明确的寄件人和收件人。
- 信件有送达时间、状态、历史归档，必须绑定账号。
- 关系链、收件箱、邮戳、地理位置都需要长期保存。

建议：

- MVP 支持手机号 / 邮箱 / 微信登录中的一种即可。
- 不要一开始做复杂个人主页。
- 注册后只要求用户设置：昵称、头像、常驻城市。
- 精确地址不要强制填写，隐私风险太高。

### 1.2 如何发展用户？

这个产品天然不是广场型产品，而是关系型产品。冷启动应该依赖“邀请一个具体的人来收信”。

推荐增长路径：

1. 用户写完第一封信。
2. 系统生成一个邀请链接。
3. 用户把链接发给微信/QQ/短信里的某个人。
4. 对方打开链接后注册/登录，收下这封信。
5. 两人之间形成一个“通信关系”。

也就是说，增长机制不是“来注册一个 App”，而是：

> 有人给你写了一封信，正在路上。

这比普通邀请更有情绪价值。

### 1.3 如何指定我要寄信的人？

结论（Neil 已确认，替代原「三层」方案）：

- **已知对方公开 ID**：填写 ID，或从通信簿选择。
- **对方尚未注册**：填写称呼，生成一次性邀请链接（可过期、可选口令）；不要求对方预先有 ID。
- **认领后**：对方注册/登录 → 认领信件 → 分配或沿用公开 ID → 建立通信关系 → 之后用 ID 互寄。
- 链接可先展示「有人给你写了一封信」再要求注册；认领时可设昵称备注；公开 ID 可选自定义唯一短码，认领仍以链接为主。
- **不做**邮箱/手机号搜人，**不做**广场发现；陌生人笔友/漂流瓶等不纳入当前已确认路线。

## 2. 功能创新：随机漂流瓶

原探索方向，暂不纳入已确认路线。Neil 已确认产品服务具体通信关系，不做广场搜人；以下仅保留为历史设想，不构成后续开发承诺。

### 2.1 可以做什么

#### 漂流瓶寄信

用户可以选择“寄给未知的人”。

- 系统随机选择一个收件人。
- 或随机投递到某个城市的邮局。
- 对方收到后可以选择回复，也可以不回复。

#### 随机捞信

用户可以在地图上的某个邮局“捞一封信”。

- 类似从邮筒/海边捞出一封陌生人的信。
- 可以按城市、国家、主题、心情筛选。

#### 城市邮局墙

每个城市邮局可以有一个公共信箱。

- 用户可以投递匿名/半匿名信件。
- 其他人可以在这个城市邮局看到部分公开信。

### 2.2 必须注意的问题

陌生人通信会带来内容安全问题：骚扰、广告、色情、诈骗、引流。

所以漂流瓶不能第一天就完全开放，建议：

- 先做好友之间的寄信闭环。
- 再做“审核后公开”的漂流瓶。
- 限制每日投递数量。
- 支持举报、拉黑、内容过滤。
- 未成年人相关内容要谨慎。

## 3. 配送与定位

### 3.1 怎么确定收信人的地理位置？

不要用精确定位作为基础能力。产品需要的是“邮政位置感”，不是实时 GPS。

推荐方案：

#### MVP：常驻城市

用户注册时选择一个常驻城市，例如“深圳”“成都”“北京”。

优点：

- 隐私风险低。
- 用户理解成本低。
- 足够计算距离和运输时间。
- 适合地图邮局玩法。

#### 第二阶段：多个收信地址

用户可以设置多个虚拟地址：

- 家乡邮局
- 学校邮局
- 公司邮局
- 当前城市邮局

这里的地址仍然可以只精确到城市/区县，不需要门牌号。

#### 第三阶段：临时旅行位置

用户可以选择“我正在某个城市旅行”，信件可以寄到当地邮局。

这会让产品更有旅行感和现实感。

### 3.2 是否要用真实 GPS？

不建议强依赖。

可以作为可选增强：

- 自动推荐附近邮局。
- 判断用户是否在某个城市。
- 做“到本地邮局才能寄出”的仪式感。

但核心身份位置应该由用户主动设置，而不是持续定位。

### 3.3 运送时间怎么算？

建议用“真实地理距离 + 产品化压缩”。

例如：

- 同城：10 分钟 - 1 小时
- 同省：1 - 6 小时
- 跨省：6 - 24 小时
- 跨国：1 - 3 天

真实邮政可能更慢，但产品上线初期不能让用户等太久。慢要有期待感，不能变成流失。

## 4. 还需要考虑的其他问题

### 4.1 隐私与安全

这是第一优先级。

需要明确：

- 信件默认私密。
- 平台是否能审核私信内容？如何说明？
- 用户是否能删除信件？删除是双方删除还是仅自己删除？
- 被寄信骚扰怎么办？
- 是否允许陌生人直接寄信？

建议：

- 好友/联系人通信默认私密。
- 陌生人信件必须有限额和举报机制。
- 漂流瓶默认可被平台审核。
- 精确地理位置不公开。

### 4.2 内容生命周期

要决定信件是不是永久保存。

可选设计：

- 普通信：永久归档。
- 限时信：打开后保留一段时间。
- 未来信：指定未来某天送达。
- 纪念信：每年同一天重新提醒。

其中“未来信”非常适合这个产品，可以作为第二阶段强功能。

### 4.3 产品边界：是社交还是工具？

推荐定位：关系型慢社交，不是效率工具。

不要做成邮箱替代品，也不要做成即时聊天。

应该服务这些场景：

- 情侣异地写信
- 好朋友长期通信
- 家人之间写不出口的话
- 写给未来的自己
- 陌生人笔友
- 旅行明信片

### 4.4 通知策略

通知不能太像 IM。

建议：

- “你有一封信正在路上”
- “来自成都的信已到达深圳邮局”
- “对方打开了你寄出的信”

但不要出现：

- 已读秒回压力
- 正在输入
- 连续催回复

### 4.5 商业化可能

短期不急，但可以预留。

可能方向：

- 付费信纸、邮票、信封
- 纪念邮戳
- 会员：更多归档空间、更多未来信
- 实体明信片/实体信件打印寄送
- 情侣纪念册导出

其中最自然的是：数字信件 → 实体打印寄送。

### 4.6 法务与合规

如果涉及用户生成内容和陌生人通信，需要考虑：

- 用户协议
- 隐私政策
- 内容举报
- 账号封禁
- 数据删除
- 未成年人保护

MVP 可以先小范围测试，但上线前不能完全忽略。

## 5. 推荐的产品路线

### Phase 1：熟人寄信闭环

目标：验证“慢信件”是否真的有情绪价值。

功能：

- 注册/登录
- 写信
- 字数限制
- 信纸实时预览
- 邀请链接指定收件人
- 常驻城市
- 地图邮局寄信
- 延迟送达
- 邮戳打开
- 双方通信记录

### Phase 2：关系增强

目标：让用户持续使用。

功能：

- 联系人列表
- 往来书信时间线
- 未来信
- 特殊邮票/信纸
- 纪念日提醒
- 多城市邮局

### 明确下一阶段：用户 ID + 邀请认领

Neil 已确认，替代原「陌生人慢社交」作为近期路线；对应开发规划中的 Phase 3。

- 唯一公开用户 ID；支持先注册拿 ID 再写信。
- 一次性邀请链接认领（有效期、可选口令）。
- 注册/登录后认领，分配或沿用 ID，建立通信关系。
- 后续通过 ID / 通信簿互寄。
- 不做广场搜人；验收标准见[开发规划](development-plan.md)。

（漂流瓶、城市公共邮局、笔友匹配等仅作历史设想，不构成当前开发承诺。）

## 6. 当前最重要的判断

这个产品真正的难点不是技术，而是边界：

- 慢到有仪式感，但不能慢到没人用。
- 真实到有代入感，但不能真实到侵犯隐私。
- 陌生人玩法有趣，但不能失控成垃圾内容池。
- 复古是外观，等待机制才是核心。

MVP 应该先服务“我想认真给某个人写一封信”这个场景。

下一阶段先落实用户 ID 与邀请认领闭环；其他探索不视为已确认开发承诺。
