# 纸短情长：产品概念整理

## 一句话定位

纸短情长是一个 Web 端慢通讯 App：用数字方式模拟八九十年代写信、寄信、等信、收信的完整邮政体验，让用户重新感受“交通慢、书信慢，所以情感更重”的交流仪式感。

## 核心体验

这个产品不是一个更快的聊天工具，而是一个刻意变慢的情感沟通系统。

用户写下一封有限字数的信，必须像现实中一样到“当地邮政局”寄出。信件会根据寄件人和收件人的真实地理距离，经历一段可视化的运输时间，最终送达对方。对方打开信件时，会看到信纸、邮戳、寄送轨迹和正文内容。

## 产品关键词

- 慢通讯
- 写信仪式感
- 地理真实感
- 邮政系统模拟
- 等待与期待
- 长期关系记录
- 纸短情长

## 用户流程

### 1. 写信

用户进入写信界面后，在输入框中输入内容。

设计重点：

- 信件内容有字数限制，不能无限写。
- 输入内容实时渲染到信纸上，而不是普通聊天输入框。
- 视觉上应该像“正在写一封真的信”。
- 可以考虑信纸样式、字体、署名、日期等元素。

### 2. 选择收件人

用户选择要寄给谁。

设计重点：

- 收件人需要有一个地理位置。
- 可以先从好友/联系人系统开始，后续再扩展陌生人或公开信箱。

### 3. 到邮政局寄信

寄信不是点击“发送”就完成，而是必须在地图上的当地邮政局进行寄出操作。

设计重点：

- 地图上分布不同地区的邮政局。
- 用户只能在自己所在地附近的邮政局寄信。
- “寄出”动作要有仪式感，例如盖章、投入邮筒、生成邮戳。

### 4. 信件运输

信件寄出后进入运输状态。

设计重点：

- 运送时间根据寄件人和收件人的真实地理位置计算。
- 国内、省内、跨国可以有不同速度。
- 地图上展示信件运输路径或状态节点。
- 用户能看到“已揽收 / 离开发件地 / 中转中 / 到达收件地 / 派送中 / 已送达”等状态。

### 5. 收信与打开

信件送达后，收件人可以打开。

设计重点：

- 打开信件时展示信纸、正文、寄件时间、送达时间、邮戳。
- 邮戳可以包含寄件地、收件地、日期。
- 这封信应成为长期关系记录的一部分，而不是阅后即焚。

## 功能模块拆分

### 写信模块

- 字数限制
- 实时信纸预览
- 信纸样式
- 草稿保存
- 署名和日期

### 地图邮政模块

- 地图展示
- 邮政局点位
- 用户当前位置或常驻城市
- 本地邮政局寄信入口

### 信件运输模块

- 地理距离计算
- 运送时间计算
- 信件状态机
- 地图轨迹展示
- 到达通知

### 收信模块

- 收件箱
- 未读信件
- 打开动画
- 邮戳展示
- 信件归档

### 关系记录模块

- 与某人的往来书信时间线
- 按日期、地点、主题回看
- 长期保存一段关系里的书信记录

## MVP 建议

第一版不要一上来做完整国际邮政系统，先做一个小而完整的闭环：

1. 用户可以写一封限制字数的信。
2. 信件实时显示在信纸上。
3. 用户选择收件人和寄件城市。
4. 系统根据两地距离生成一个延迟送达时间。
5. 地图上显示寄件地、收件地和运输状态。
6. 到时间后收件人可以打开信，并看到邮戳。

MVP 的重点不是功能多，而是让用户第一次感受到：这不是聊天，这是寄信。

## 产品气质

这个 App 的核心不是效率，而是克制。

它应该故意避免即时通讯的习惯：

- 不追求秒回。
- 不鼓励碎片化短消息轰炸。
- 不把“发送”做得太轻。
- 不让用户随便撤回、修改已经寄出的信。

产品要让用户意识到：写下来的话会被寄出去，会经过时间，会留下痕迹。

## 可以进一步探索的问题

- 是否允许用户设置“真实地址”，还是只精确到城市？
- 信件运输时间应该真实到几小时/几天，还是做游戏化压缩？
- 是否需要邮票、信封、信纸这些可收集元素？
- 是否支持情侣、朋友、家人等不同关系类型？
- 是否允许陌生人笔友系统？
- 是否做成 PWA，增强移动端体验？

## 暂定结论

纸短情长的核心不是复古皮肤，而是“慢”的机制本身。

只要写信、寄信、等待、收信这四个环节形成闭环，产品的情绪价值就能成立。
